# 작업 맥락

- 2026-11-11. 사용자는 공개 뷰티 페이지를 보여주며 뷰티 사업자 회원가입과 관리를 위한 아이디어 및 PRD를 요청했다.
- 현재 `/apply`는 구글 로그인 후 브랜드 분야를 선택해 신청한다. 브랜드명·담당자·이메일·전화·소개를 받지만 사업자 증빙 항목은 없다.
- `createPartnerApplication`은 `designers.approval_status='approved'`와 작업공간 `status='active'`를 즉시 저장한다. `/apply` 화면의 `Reviewing` 표시 및 일부 로그인 안내와 실제 권한 상태가 다르다.
- `/dashboard/beauty`에는 브랜드 프로필, 상품, 캠페인·매칭, 제안, 콘텐츠, 성과·주문, 정산 화면이 있다. 관리자에게는 브랜드·회원·상품 관리 기능이 있다.
- `products.approval_status`는 기본적으로 승인이고 환경 설정이 명시적으로 false일 때만 신규 상품이 대기 상태다. PRD는 사업자 승인과 상품 공개를 별도 관문으로 제안한다.
- 이번 문서는 구현 제안이다. 운영 DB의 실제 사업자 수, 실제 승인 상태, 외부 알림 연동은 확인하지 않았다.
- 외부 참고는 Shopify Collabs 공식 도움말의 신청·승인·협업 관리 개념만 사용한다. K-MODU에 그대로 복제하지 않는다.
- 2026-11-11 사용자 수정. 사업자등록증과 사전 승인을 원하지 않는다. 간편 가입 후 즉시 뷰티 상품을 올리고, 문제는 관리자가 사후 처리하는 방향으로 PRD를 다시 작성했다. 초기 문서의 신청 대기·상품 전수 검수 권고는 폐기한다.
- 뷰티 공개 페이지의 입점 CTA는 현재 이메일 문의다. 공통 신청 화면에는 패션 중심 표현이 남아 있다. 뷰티 가입 화면은 분리하고 기존 구글 로그인, 사용자, 브랜드, 작업공간, 뷰티 센터는 재사용하는 안이다.
- 관리자 브랜드 비활성 API는 현재 designers.approval_status만 disabled로 바꾼다. 공개 카탈로그에서는 제외되지만, requireBeautyPartner/getSelectedPartnerForApi는 활성 멤버십과 소유권을 보면서 designer.approval_status를 확인하지 않는다. PRD에 서버 쓰기 차단을 필수 수용 기준으로 명시했다.
- 운영자 상품 숨김은 status=hidden과 approval_status 변경이 가능하다. 파트너 상품 조회는 hidden을 제외하므로, 관리자 제재는 소유자 숨김과 구별해 표시·복구해야 한다.
